# AI 原生工程化落地 SOP · ambient-radio（梦可电台）

> 文档版本：v1.0（2026-08-19，仿《AI 原生产品工程化落地通用规范与标准 SOP》v4.2 定制）
> 适用范围：本仓的全部 AI 辅助开发——规划、实现、测试、修复、重构与体验验收。
> 核心范式：规范驱动开发（Spec-Driven）、沙盒评估工程（Harness）、上下文工程。
> 本项目特殊性：**产品本身就是 AI 原生应用**（主播梦可是 LLM + TTS 驱动），同时开发过程也由 AI 主导——两层不确定性叠加，工程化约束加倍重要。

## 0. 术语与规模适配

| 术语 | 在本项目的落地形态 |
| --- | --- |
| **Harness 沙盒** | Vitest 测试套件 + 注入式假依赖（确定性 rng、显式传入的 now、内存 Track）。core 的「考场」。 |
| **虚拟时钟** | 本项目的实现方式：引擎与调度器的所有时间感知都是显式参数（`tick(now)`、`pickNext(now)`），测试里直接传数字。不需要 mock 计时器——时钟本来就是注入的。 |
| **Stub 桩服务** | 组装层的 LLM/TTS/存储接口在测试中用内存假实现替换；真实外部调用永不被测试触达。 |
| **DAG 任务拆解** | 里程碑（P1→P2→P3）+ 里程碑内的垂直切片（一个测试→一个实现→循环）。 |
| **品味门禁（Vibe Check）** | 维护者亲耳收听。P1 结束的标志写进了技术方案：「维护者自己连听 30 分钟不想关」。 |
| **上下文工程** | `AGENTS.md`（入口宪法）+ PRD/技术设计编号体系（FR/D）+ `.agents/skills` 按需加载 + 会话拆分纪律。 |

**规模适配声明**：本项目是单人 + AI 协作的中型单仓，六层全部适用，但以「本地可执行」形态落地（无 CI 流水线，验证合同见《团队协作与开发规范》§9）。

## 1. 六层架构在本项目的映射

通用 SOP 的六层元架构，逐层对照本项目的现状：

```text
第 1 层：意图锁定层 ──── PRD（FR/CR/ER 编号）+ 技术设计（D1~D9 灵魂决策）  【已落地】
第 2 层：契约硬化层 ──── TypeScript strict + shared schema + core types
                         + station.config.json（参数全部外置）          【已落地】
第 3 层：Harness 沙盒 ── Vitest + 注入式 rng/clock + 内存假依赖          【core 已落地，adapters 随做随建】
第 4 层：熔断与回滚 ──── 3 次重试上限 → git stash → 上报维护者           【本文 §3】
第 5 层：DAG 任务拆解 ── P1/P2/P3 里程碑 + 垂直切片 + 单会话单任务       【持续执行】
第 6 层：品味门禁层 ──── 维护者收听验收（Vibe Check）+ 灵魂决策门禁      【本文 §4】
```

### 1.1 意图锁定：编号即语法

通用 SOP 推荐 EARS 语法；本项目的 PRD 已用编号体系承担同等职责，**沿用即可，不强改**：

- 需求引用格式：`FR-031`（主动串场频率）、`ER-001`（语音失败音乐继续）、`CR-005`（不伪造人类身份）、`D2`（LLM 不选歌）。
- AI 写代码、写测试、写提交信息时，**用这些编号说话**。测试注释里标 FR 编号（已在 core 测试中实践），审查时即可机械对照。
- 新需求进 PRD 时沿用 `FR-XXX` 风格；不可变规则（Invariants）= 灵魂决策 D1~D9；非目标（Non-Goals）= PRD §8.2「不包含」清单——**那份清单对 AI 尤其重要**，它列的几乎全是 AI 默认想加的东西（暂停、字幕、切歌、个性化）。

### 1.2 契约硬化：类型与配置双锁

- **类型锁**：`packages/shared` 是前后端协议唯一来源；`packages/core/src/types.ts` 是数据模型唯一来源。改它们 = 档位 3 流程（见《团队协作与开发规范》§4）。
- **配置锁**：一切节奏参数（说话间隔、SLA、ducking 曲线、供应商）住在 `station.config.json`；core 的 `config.ts` 是镜像。**判断一个值该放哪**：电台运行时可能想调的 → 配置；反映代码结构本身的 → 类型。
- **人格锁**：`config/persona.md` 只读（L0 层）。这是本项目最特殊的「Schema」——梦可不可被节目经历改写的部分（FR-073）。

### 1.3 Harness：确定性考场

core 的可测性来自三条注入纪律（已在引擎与调度器中实践，后续模块照办）：

1. **rng 注入**：一切随机（选曲轮盘、间隔采样、topic 升级）来自 `rng: () => number`，测试用固定值或固定序列。
2. **时间显式**：一切时间感知来自参数 `now: number`（epoch ms），测试里传数字即可模拟任意时刻——深夜时段、30 分钟滑窗过期、60 秒超时，全部毫秒级推演。
3. **依赖不创建**：模块只接收依赖（tracks 数组、config 对象），不自己读文件、连网络。

**断言矩阵**（通用 SOP 三维度 → 本项目对照）：

| 维度 | 本项目断言 | 示例 |
| --- | --- | --- |
| 功能 | 状态机迁移、决策正确性 | 串场到期规划、自然节点播出、滑窗防重复 |
| 边界与降级 | 失败静默、超时丢弃、曲库不足放宽 | `生成失败的段落被静默丢弃`、`曲库不足放宽标记` |
| 非功能/SLA | P2 起：留言响应 SLA、ducking 曲线参数 | （留言 30~90s 回应在 P2 补齐时建立） |

## 2. AI 执行工作流（个人开发实操）

本仓已装 `.agents/skills/`（Matt Pocock 工作流技能），与通用 SOP §7 的流程一一对应：

### 2.1 新功能（走档位 3）

```text
/grill-with-docs   → 拷问需求模糊点（"合适的节点"是多少秒？"平滑"是几秒？），
                     对照 PRD/技术设计消除歧义；产出 CONTEXT 与 ADR 级别的决定
        ↓
/prototype         → 纸面解决不了的（状态模型、UI 交互、听感）先做一次性原型；
                     原型代码用完即删，只保留结论
        ↓
/to-spec           → 生成实施规格，维护者批准
        ↓
/to-tickets        → 拆成单会话垂直切片（tracer-bullet），声明依赖关系
        ↓
/implement         → 每个切片新开会话；内部走 /tdd 红绿循环；
                     完成后 /code-review 审查 diff → 验证全绿 → commit
        ↓
Vibe Check         → 体验可感知的改动，请维护者亲耳收听
```

### 2.2 紧急 Bug（不走规格）

```text
/diagnosing-bugs   → 先建立复现（红），再定位根因，修复后回归测试保绿
                     不经过 /to-spec 与 /to-tickets——直接修、直接提交
```

### 2.3 会话纪律（上下文工程）

- **一个会话一个任务**。需求访谈（/grill）和实现（/implement）分属不同会话；中间用 `/handoff` 衔接（交接文档存系统临时目录，不进仓库）。
- **上下文将满时**：`/handoff` 压缩交接，新会话续作；不要在一个会话里连续 /implement 多个切片。
- **阶段中途不 compact**；阶段切换才压缩。
- **每个会话开头**：AI 自动读 `AGENTS.md`；涉及行为改动时先 read PRD 对应章节——这是铁律不是建议。

### 2.4 代码库健康（空闲时）

`/improve-codebase-architecture` 扫描可深化的模块（浅模块、漏 IO 的 core、硬编码的参数），选定一个方向当新需求走 §2.1。

## 3. 熔断与安全回滚协议

**重试上限**：对任何单个任务，Harness（测试）连续失败最多重试 **3 次**。

**第 3 次仍失败时，执行安全回滚**（Windows PowerShell）：

```powershell
git stash push -m "agent-failed-attempt-$(Get-Date -Format 'yyyyMMdd_HHmmss')"; git reset --hard HEAD
```

（bash 环境等价：`git stash push -m "agent-failed-attempt-$(date +%Y%m%d_%H%M%S)" && git reset --hard HEAD`）

然后**熔断上报**：停下，向维护者报告结构化诊断——

- 失败的断言 / 测试名
- 期望值 vs 实际值
- 最后一次有效的状态（引擎在哪个状态机位置、最后一条事件）
- 已尝试的 3 个方向与各自失败原因
- 可行的假设（Task 拆太大？seam 定错？规格本身矛盾？）

**绝对禁止**（No Assertion Bypassing）：

- 不得改测试阈值、删断言、删测试用例来「通过」
- 不得 `skip`/`todo` 掉失败测试
- 不得为了绿而放宽类型（`any`、`@ts-ignore`、关闭 strict 检查）

**作用域锁定**：实施一个切片时，只编辑该切片声明的文件范围；需要越界（比如要动 shared 类型）时先说明理由并确认——通常意味着切片拆错了。

## 4. 人类品味门禁（Human Gatekeeping）

以下节点**硬性触发维护者介入**，AI 必须自动暂停：

1. **灵魂决策门禁**：改动触碰 D1~D9 或 PRD 边界（例：给面板加暂停按钮、显示文字回复、接入在线音源、让 LLM 参与选歌）→ 停下上报，等维护者裁决。
2. **契约门禁**：修改 `shared` schema、SQLite 表结构、`station.config.json` 的参数结构 → 说明迁移影响，维护者确认后推进。
3. **Vibe Check（里程碑体验门禁）**：每个里程碑完成 → 构建可运行版本 → 维护者亲自收听。P1 的验收标准是技术方案原文：**维护者自己连听 30 分钟不想关**。听感不对的地方记录「症状 + 时段」，不用代码语言描述。
4. **熔断门禁**：§3 的 3 次失败熔断。
5. **声音门禁**：TTS 供应商/音色的最终选择（盲听 A/B）永远由维护者的耳朵决定，AI 只准备对比材料。

## 5. 已写入 AGENTS.md 的三条最小约束

（对应通用 SOP §7.6，从真实失败模式提炼，覆盖 80% 的 token 浪费场景）

1. **产品规格优先**：涉及业务逻辑、交互流程、字段定义，必须先 read PRD 再实现，禁止凭记忆推断。本产品的边界大量反 AI 直觉（详见 `AGENTS.md` 铁律 1）。
2. **修改前读全貌**：先读组件、父组件、相关样式；同一文件编辑超过 3 次仍不过，停下来重新确认意图——是任务拆太大了，往回拆一层。
3. **操作前全局扫描**：「去掉 X / 修改 Y」时，先 `rg` 检查全局同类元素一并处理。

## 6. 不良实践与纠正（电台项目版）

| 不良实践 | 本项目的典型表现 | 纠正 |
| --- | --- | --- |
| **AI 不读 PRD** | 给面板顺手加暂停按钮、显示字幕、「当前歌单」列表、点赞——全是 PRD §8.2 明令禁止的 | 会话开头读 PRD；AGENTS.md 铁律 1 点名反直觉边界；审查清单里逐条对照 |
| **播放器化漂移** | 「顺手优化」时加入进度条、切歌逻辑、倍速——产品从电台漂成播放器 | 任何 UI 元素新增前问一句：FR-001 允许吗？电台不做播放器是 D 级决策 |
| **编造节目历史** | 主播 prompt 里出现「上周我们聊过……」但数据库里没有这条记忆 | 上下文只含结构化核实记录（§4.3 防编造机制）；测试覆盖「无记录则不提及」 |
| **人格漂移** | 觉得 persona.md 太素，AI 自动「丰富」梦可的人格 | persona 只读（FR-073）；人格生长只发生在 L1 记忆，且由维护者审查 |
| **碎片化反馈** | 听到一个体验问题就发一条，AI 逐个读文件逐个改，面板被编辑 30+ 次 | 扫完整段收听体验，把所有问题一次性发；最高优先级放第一条 |
| **不叫停** | AI 连续失败，维护者说「继续」，AI 换个姿势继续失败 | 失败 2 次即停：读 `git diff`，用自己的话重新描述需求；不发「继续」 |
| **任务过大** | 一个会话里做完「留言+点歌+记忆」整块功能，上下文反复压缩后质量崩塌 | 垂直切片：一个测试→一个实现；/to-tickets 拆分；每切片独立会话 |
| **未沉淀的项目约束** | 每次会话口头重复「不许加歌单」「梦可不识字幕」 | 已写入 AGENTS.md（§5 三条 + 铁律区）；新约束发现即回写文档 |
