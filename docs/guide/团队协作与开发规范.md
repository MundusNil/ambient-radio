# 团队协作与开发规范 · ambient-radio（梦可电台）

> 适用范围：`ambient-radio` 单仓（pnpm workspaces monorepo：TypeScript core + Hono 守护进程 + Vue 3 收音机面板 + SQLite + 本地曲库）。
> 读者：维护者本人，以及协助本仓开发的 AI 编程助手（pi / Claude / Codex 等，均读根目录 `AGENTS.md`）。
> 目标：让任何一次改动——无论是人类还是 AI 做的——都在不破坏产品边界、不猜需求的前提下，可验证、可回滚。
> 性质：本项目是**单人 + AI 协作**项目。规范因此比多人团队轻（无 PR 流程、无 CI 流水线），但验证纪律不降级。

---

## 0. 怎么用这份文档

- **首次参与**：先读第 1、2、3 节（原则、词汇、结构），再读 PRD 与技术设计的灵魂决策（D1~D9）。
- **日常改动**：按第 4 节判断改动档位，用第 10 节自检清单收尾。
- **使用 AI 助手**：AI 必须先读 `AGENTS.md`；涉及行为的改动先指向 PRD 对应 FR；AI 不得猜测 API 地址、密钥、模型行为或产品边界。
- **规则不清楚**：先查 PRD → 技术设计 → 本文档 → `git log`；仍不明确就停下问维护者，**不能用默认值代替业务决定**。
- 本文档与 `AGENTS.md` 冲突时，以本文档为准并回改 `AGENTS.md`；与技术方案冲突时，以维护者最新确认为准并同步修订文档。

## 1. 一句话原则

> **产品行为要有权威来源（PRD），节奏与架构要有灵魂决策（D1~D9），运行结果要能被验证（测试），未确认的边界不能靠猜补全。**

这个产品有大量「反直觉」的边界（不做播放器、不显示文字、不识别听众），一次看似普通的改动——比如顺手加个暂停按钮——就足以摧毁产品定位。因此：

- 能用测试、类型检查、构建验证的规则，不依赖口头记忆。
- PRD 是行为唯一真相；技术设计是架构唯一真相；AI 不得用「常识」或「通用最佳实践」反向放宽它们。
- 电台重启不失忆、主播不编造过去、人格不被节目改写——这三条是产品的命，对应的技术约束（时间线可重建、记忆只收核实记录、persona 只读）优先级高于一切便利性。
- 不确定时明确报出阻断项；不要实现一个「先跑起来」的替代方案并把它当成已确认行为。

## 2. 名词小词典

| 名词 | 大白话解释 |
| --- | --- |
| **梦可** | 唯一的 AI 主播。知道自己由代码构成，不假装人类。人格档案 `config/persona.md`。 |
| **维护者** | 电台的制作人（本仓唯一人类），拥有所有业务决定权。 |
| **节目引擎** | 电台大脑（`packages/core/src/engine`）。每秒 tick 的状态机，只决定「何时说话、开什么段落」，不管「说什么」（那是 LLM 的事）。 |
| **段落 segment** | 梦可一次完整开口。五种类型：台呼 / 串场 / 小主题 / 回应留言 / 点歌受理。 |
| **自然节点** | 允许开口的时机：曲目边界，或曲目中段的安全窗口（前奏 20s、尾奏 10s 保护，绝不打断开头）。 |
| **曲库调度器** | 确定性选曲器（`packages/core/src/scheduler`）。加权随机 + 30 分钟防重复 + 时段修正 + 近期惩罚。**LLM 永远不选歌（D2）。** |
| **调频进入** | 听众打开页面时直接跳进正在进行的节目。电台 24/7 常开，音乐永远「已经在放」。 |
| **开台 / 关台** | 听众视角的进入 / 离开。不是电台的开关——电台（守护进程）一直都在。 |
| **ducking** | 梦可说话时音乐平滑降到 22%，说完约 1.2s 后恢复。 |
| **空房间沉默** | 无人收听时主播不说话、不积累记忆（`speakWhenAlone=false`，可配置）。 |
| **L0 / L1 / L2** | 三层记忆：L0 人格（persona.md，只读）/ L1 节目记忆（策展写入、分层衰减）/ L2 临时上下文（随会话消散）。 |
| **沉默保底** | 段落生成失败或来不及时直接放弃：音乐继续、主播沉默、绝不向听众播报技术错误（ER-001~003）。 |
| **组装层** | `apps/station`：把 core 的意图事件翻译成真实 IO（调 LLM、TTS、写库、广播 WS）。 |
| **曲库** | `config/library/<子风格>/`，文件夹名即标签。音频文件不进 git。 |
| **seam** | 模块的公共接口面。测试只走 seam，不伸进实现内部。 |

## 3. 项目长什么样

```text
ambient-radio/                     # pnpm workspaces + TypeScript strict
├─ packages/
│  ├─ core/            # 电台大脑：引擎、调度器、上下文构建、记忆（纯逻辑，零 IO）
│  ├─ adapters/        # 协议实现：LLM（DeepSeek）/ TTS / SQLite / 音频 / 时钟
│  └─ shared/          # API / WS 事件 schema（前后端共享契约）
├─ apps/
│  ├─ station/         # 电台守护进程：Hono + ws，组装一切，24/7 常驻
│  └─ web/             # 收音机面板：Vue 3 + Web Audio（ducking 在这里发生）
├─ config/
│  ├─ persona.md       # 梦可的人格档案（L0，只读）
│  ├─ station.config.json  # 全部可调参数（调电台=改配置）
│  └─ library/         # 曲库根目录，子文件夹名 = 子风格标签
├─ docs/
│  ├─ product-requirements.md     # PRD
│  ├─ technical-design.md         # 技术设计（D1~D9）
│  └─ guide/            # 本文档 + AI 工程化 SOP
├─ .agents/skills/     # 16 个编码工作流技能（tdd/implement/code-review/...）
├─ .env / .env.example # API key（.env 不进 git）
└─ AGENTS.md           # AI 入口宪法
```

运行链路：

```text
浏览器（收音机面板）
  → HTTP /api/state + WS → 守护进程 station（Hono）
     → core 节目引擎（tick 意图事件）
     → core 调度器（选曲决策）
     → adapters（LLM 文案 → TTS 语音 → SQLite 持久化 → ffmpeg 响度归一）
     → config/library（音频文件流）+ SQLite + persona.md
```

关键认知：**web 不直接碰任何数据**，只吃 `/api/state` 契约和 WS 事件；**core 不知道 IO 存在**；电台崩溃重启后从 SQLite 重建时间线（电台重启不失忆）。

### 工具链上位替代

存在上位替代时，禁止继续使用下位方案：

| 下位方案 | 上位方案 | 使用规则 |
| --- | --- | --- |
| `.js` / `.jsx` | TypeScript `.ts` | 全仓源码统一 TS strict；测试与工具代码同。 |
| `npm` / `npx` | `pnpm` / `pnpm dlx` | 依赖、脚本、一次性 CLI 统一 pnpm；只维护 `pnpm-lock.yaml`。 |
| `grep` / `find` | `rg` / `rg --files` | 仓库内搜索优先 ripgrep。 |
| 手搓目录结构 | 官方脚手架 | 新 app / 新工具优先官方生成器（`pnpm create vite`、`pnpm create hono`），生成后再改造。 |
| 节奏参数写进代码 | `station.config.json` | 所有可调参数进配置；core 的 `config.ts` 保持镜像。 |
| 直接改代码调行为 | 先读 PRD 对应 FR | 行为变更必须能引用到需求编号或维护者明确指示。 |

## 4. 开发流程：按改动大小选择档位

不要把复杂流程套在错别字上，也不要把产品边界的改动当作小修。

### 档位 1：琐碎改动

适用于错别字、文档修正、不改变接口或行为的样式调整。

- 直接修改并跑相关验证（受影响的包 `tsc` / `biome check`）。
- 不需要规格或拆票。

### 档位 2：Bug 修复

适用于让已有行为恢复到已定义的规格（PRD / 技术设计 / 测试所描述的行为）。

- 必须先复现，并增加覆盖根因的回归测试（先红后绿）。
- 不得用吞异常、放宽校验、增加未说明的 fallback 掩盖问题。
- 用 `.agents/skills/diagnosing-bugs` 的诊断循环，不要连续猜测式改动。

### 档位 3：新功能或边界变化

适用于新增能力、改 API/WS 契约、改数据库表、改段落类型、改记忆结构、引入新外部服务或触碰灵魂决策。

```text
1. 读 PRD 对应章节 + 技术设计对应子系统；确认不与 FR/CR/ER/D 冲突
2. 关键不确定性先消除：/grill-with-docs（拷问需求）、/research（查证）、/prototype（一次性原型验证设计）
3. 较大改动用 /to-spec 生成本地实施规格，维护者批准后为准
4. 用 /to-tickets 拆成单会话垂直切片
5. 每个切片：/implement + /tdd 实施 → 全量验证 → /code-review 自审 → 提交
6. 体验可感知的改动：请维护者亲自收听（Vibe Check）
```

**灵魂决策变更的额外门禁**：任何触碰 D1~D9 的改动（例：想接入在线音乐 API = 触碰 D3；想让 LLM 选歌 = 触碰 D2），必须由维护者显式重新确认并修订技术设计文档后才能动代码。AI 发现自己正在触碰时，立即停下上报。

## 5. 分支、提交与落主线

**目标流程（配置远程仓库后即刻生效）**：不直接更新远程 `main`；工作在 `feat|fix|chore|docs/<主题>` 分支上进行（小写 ASCII kebab-case），通过 PR 合入。「落主线」的完整流程（PR 边界判断、推送前验证、rebase、中文写入验证、分支清理）以 [land-main-workflow.md](land-main-workflow.md) 为唯一详细流程来源。

**当前过渡（单人本地阶段，尚未配置 remote）**：在本地 `main` 上小步提交，用两个纪律作为交换：

- **提交原子性**：一个提交只做一件事（一个切片、一个修复、一个文档）；混合主题必须拆分。回滚的最小单位是提交，不是文件。
- **提交前验证**：每次提交前本地三件套全绿（§9）。

**提交信息规范（双语，即刻生效）**：中英双语 Conventional Commits——`<type>(<scope>): <english-description>  <中文描述>`。type 用 `feat / fix / chore / docs / test / refactor`（小写 ASCII）；scope 必填，用包名或目录（core / scheduler / engine / station / web / shared / adapters / config / docs）；英文描述与中文描述之间两个空格。示例：`feat(engine): add natural node window  增加自然节点窗口`。提交正文写清楚动机与验证方式（哪些测试覆盖、跑过什么命令）。

## 6. 代码怎么放

### packages/core（电台大脑）

- **零 IO 铁律**：不 import 网络、文件、数据库、系统时钟；一切外部依赖（rng、now、存储接口）由参数注入。这是「引擎可以在 CLI 里用假时钟跑单元测试」的根基。
- 模块用「深模块」标准设计：小接口、大行为（参考 `.agents/skills/codebase-design` 的词汇）。新模块先写 seam 再写实现。
- 数据契约（`types.ts`）与 SQLite 表一一对应；改契约 = 改表结构，走档位 3。
- 配置类型（`config.ts`）是 `station.config.json` 的镜像，两边必须同步改。

### packages/adapters（协议层）

- 每个外部系统一个子模块（llm / tts / store / audio / clock），统一由组装层注入 core。
- 适配器之间不互相 import；换供应商 = 换适配器实现 + 改配置，core 零感知（D7/D8）。

### packages/shared（契约）

- 前后端唯一共享包：API 响应与 WS 事件的类型定义。**web 只准依赖这一个包**，不许 import core。
- 改这里的类型 = 改协议，前后端一起改，走档位 3。

### apps/station（组装层）

- 组装职责：读配置、构建 adapters、驱动引擎 tick 循环、响应意图事件（生成段落）、广播 WS、REST、静态资源与音频流。
- 路由层保持薄；业务节奏判断都在 core 里，组装层不做「何时说话」的决定。
- 生成流水线失败必须静默降级（沉默保底），绝不向听众暴露错误。

### apps/web（收音机面板）

- 界面元素只有：进入/离开、总音量、唯一留言输入框、本会话自己的留言列表（FR-001/050/052）。
- **禁止出现**：主播文字回复、字幕、歌词、切歌/暂停/进度条/点赞点踩、任何模式切换（PRD §8.2 是完整清单）。
- 音频：Web Audio 双音源（音乐 + 语音）+ GainNode ducking；曲线参数来自配置，不硬编码。
- 视觉：一张收音机面板 + 极少量动效（ON AIR 灯、说话呼吸感）。为美学生长留缝但不预建（D4）。

## 7. 安全与数据红线

### 7.1 不硬编码、不猜配置

- API key 只存在于 `.env`（gitignore）；代码引用环境变量名（`apiKeyEnv`），不引用值。
- `.env` 永不提交；发现 key 泄漏进 git 历史，立即在供应商控制台轮换。
- 未配置的必需值必须显式失败，不得用假 URL、空 key、示例值继续运行。

### 7.2 隐私与内容边界

- 原始留言 7 天自动删除（FR-092）；测试与文档中不得使用真实留言内容。
- 匿名摘要不得含用户名、原句、个人生活细节（FR-082）；记忆写入必须走策展（`extractMemory`），禁止把原始留言直接转成长期记忆（FR-093）。
- 主播内容边界（CR-001~007）是产品红线；任何「让梦可更活泼一点」的实现都不得越过。
- 曲库音频的版权责任归维护者；仓库只跟踪目录结构（`.gitkeep`），永不跟踪音频文件。

### 7.3 破坏性操作

- 删数据、删目录、`git reset --hard`、清缓存前：先确认目标范围与恢复方式。
- SQLite 是电台的记忆：动 `data/` 下任何文件前先备份。
- AI 不得自主执行不可逆删除；连续失败 3 次即熔断上报（见 AI SOP）。

## 8. 与 AI 助手协作

AI 可以加速一切，但不拥有业务决定权。

- **先喂权威来源**：PRD 的 FR 编号、技术设计的 D 编号、相关测试。让 AI 引用编号工作，而不是凭印象。
- **要求 AI 先声明 seam 与验证方式**再写实现（TDD 纪律）。
- **对 AI 的改动至少检查**：是否违反 FR（尤其播放器类功能顺手化）、是否泄漏 key、是否写了 persona.md、是否在 core 里 import 了 IO、是否把配置参数硬编码进了代码。
- **不接受「猜测可能是」**：外部 API 行为（DeepSeek 返回格式、edge-tts 端点）必须查文档或实测。
- **技能是方法论**：`.agents/skills/` 里的 tdd / code-review / grilling 等技能按需加载；新技能安装优先 SkillHub（全局策略）。
- 详细的 AI 工作流（熔断、回滚、门禁、会话衔接）见 [AI 原生工程化落地 SOP](AI原生工程化SOP.md)。

## 9. 验证合同（现状：本地验证，无 CI）

当前仓库没有 CI 流水线。**合并到 main 前（即每次提交前）必须在本地完成以下检查**，任何一项失败不得提交：

```bash
pnpm test             # Vitest 全绿（core 全部纯逻辑测试）
pnpm check            # Biome 零 error（warning 也要修，除非有书面理由）
pnpm --filter @ambient-radio/web build   # vue-tsc 类型检查 + Vite 构建
```

守护进程改动追加冒烟：

```bash
pnpm dev:station      # 启动后 curl /api/health → {"ok":true}
                     # curl /api/state → 返回 shared 契约结构
```

**Docker 化与服务器部署时**（未来）：镜像内含 ffmpeg；`config/library`、`data/`（SQLite）、`config/` 以 volume 挂载；key 走环境变量；部署后冒烟 `/api/health` + 真实收听 5 分钟。届时本节升级为部署检查表。

## 10. 提交前自检清单

**范围与规格**

- [ ] 改动能追溯到 PRD 的 FR/CR/ER 编号、技术设计的 D 编号，或维护者的明确指示。
- [ ] 未引入未经确认的外部服务、数据源或产品功能（尤其播放器化、文字化、模式化）。
- [ ] 灵魂决策未被触碰；或已获维护者重新确认并修订技术设计。

**代码与测试**

- [ ] `pnpm test` 全绿；新行为有测试覆盖；bug 修复带了回归测试。
- [ ] `pnpm check` 与 `pnpm --filter @ambient-radio/web build` 通过。
- [ ] core 没有新增 IO import；新参数进了 `station.config.json` 并同步 `config.ts` 镜像。

**安全与质量**

- [ ] 没有 key、真实 URL、内部路径硬编码；`.env` 未被跟踪。
- [ ] 日志与错误输出不含敏感信息；段落生成失败走静默降级。
- [ ] persona.md 未被任何自动流程修改。

**交付**

- [ ] 提交原子、信息符合双语 Conventional Commits（`type(scope): english  中文`，两个空格分隔）；正文写了验证方式。
- [ ] 工作树无不明来源文件；`git status` 干净。
- [ ] 体验可感知的改动已请维护者收听验证，或明确记录「待 Vibe Check」。

## 11. 遇到问题怎么办

1. 先查：README → `AGENTS.md` → PRD / 技术设计 → 本文档 → `git log`。
2. 复现后再修：保留错误、日志和最小复现；不连续猜测式改动（同一方向失败 2 次即停，读一遍 `git diff`，重新描述需求）。
3. 规范与现实冲突时，先修文档或提出决策，不让代码悄悄成为新的真相。
4. 电台体验「感觉不对」但说不出哪里不对时：描述症状 + 复听时段，交给维护者判断——体验问题用耳朵验收，不用代码验收。
